设想一个 Go 服务：`pprof` 看存活堆一直在 150MiB 上下，容器的内存上限是 256Mi，按理说还有 100MiB 的余量。实际跑起来却会反复重启，`kubectl describe` 里写着 `OOMKilled`，退出码 137。

我在本机用 kind 起了一个一次性集群，写了一个能精确控制存活堆、垃圾产生速度和堆外内存的小程序，把这个场景复现出来，再逐个测 `GOMEMLIMIT`、`GOGC`、downward API 和 `GOMAXPROCS`。结论先放这里：默认 `GOGC=100` 时堆目标约等于存活堆的 2 倍，150MiB 存活堆对应 293MiB 的目标，256Mi 的上限根本装不下；`GOMEMLIMIT=230MiB` 能让它活下来，代价是 GC 占用的 CPU 从 7% 涨到 23%（这个指标含空闲时段做的标记，偏高，算上限），而且它是软上限，存活堆继续涨时进程照样会死，只是死前先把 CPU 耗在 GC 上。

## 实验环境与测试程序

集群只为这次实验创建，kubeconfig 写在实验目录里，所有 `kubectl` 都显式带 `--kubeconfig`，结束后整个集群删掉。

测试程序叫 `memload`，`FROM scratch` 打包，镜像 2.5MB 左右。源码、Dockerfile 和跑实验的 kind 脚本放在 blog-go-example/gomemlimit，可以照着 README 复现。它启动时打印运行环境，然后按以下环境变量制造内存压力：

默认每秒输出一行（部分实验把间隔调到 200ms、100ms 或 50ms，表里的速率都已折算成每秒），数据来自 `runtime/metrics` 和容器自己的 cgroup 文件：

`live` 是 `/gc/heap/live:bytes`，`goal` 是 `/gc/heap/goal:bytes`，`runtime` 是 `/memory/classes/total:bytes` 减去已归还给系统的部分，也就是 `GOMEMLIMIT` 实际管控的那部分内存。`gcCPU` 是两次采样之间 `/cpu/classes/gc/total` 的增量除以 `/cpu/classes/total` 的增量，后者约等于 `GOMAXPROCS × 墙钟时间`。注意 `/cpu/classes/gc/total` 包含 `/gc/mark/idle`，也就是 P 空闲时顺手做的标记；`runtime/metrics` 文档说要减掉它才是 GC 必须占用的 CPU。主实验的分配被限速在 300MiB/s，2 个 P 常有空闲，所以文中的 GC CPU 都偏高，应当看成上限，比较同一组内的相对变化更可靠。`cg.cur` 和 `cg.peak` 读的是容器内的 `memory.current` 和 `memory.peak`。

早期版本的存活集用 1MiB 的 `[]byte`，这种对象不含指针，GC 不需要扫描内容，GC CPU 一直在 1% 左右，跟真实服务差得太远。后面的主实验都开了 `LIVE_PTR`，并把垃圾产生速度限制在 300MiB/s。不限速时短命对象来得太快，浮动垃圾会把测到的存活堆从 120MiB 抬到 200MiB，干扰判断，那组数据我单独拿来测吞吐。

所有 Pod 的内存上限都是 256Mi（`memory.max=268435456`），CPU 上限 2 核。requests 的内存与 limit 相同，CPU request 只给 100m，所以 Pod 属于 Burstable。

容器被杀之后，容器自己的 cgroup 也跟着消失，程序里读到的 `memory.peak` 来不及打印。我改成在 kind 节点上读 Pod 级的 cgroup，路径形如 `/sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/kubelet-kubepods-burstable.slice/kubelet-kubepods-burstable-pod.slice`，只要 Pod 对象还在，这一层的 `memory.events`、`memory.peak` 和 `cpu.stat` 就会保留，重启多次的计数也会累加。另外 `kubectl logs --previous` 在连续重启后只能拿到上一次的日志，我把节点上 `/var/log/pods` 下每次运行的日志文件也一起拷了出来，后面需要单次结果的实验则改用 `restartPolicy: Never`。

## GOMEMLIMIT=230MiB 让它活下来，GC CPU 涨到 23%

同样 150MiB 的存活集，加上 `GOMEMLIMIT=230MiB`：

表里除最后两列外单位都是 MiB，取的是 5 秒以后各采样的平均值。

设置 `GOMEMLIMIT=230MiB` 后，goal 从 344 压到 208，runtime 稳定在 228MiB 左右，Pod 峰值 240.7MiB，在 256Mi 以内。代价是 GC 次数从每秒 2.1 次升到 6.5 次，GC CPU 从 7.4% 升到 23.0%（两者都含空闲标记时间），换句话说是在用 CPU 换内存。

`GOMEMLIMIT=400MiB` 比容器上限还大，等于没设，结果和默认情况一样。

`GOGC=off` 加 `GOMEMLIMIT` 是官方 GC 指南里提到的组合：只在接近上限时才回收。当上限本身已经低于 2 倍存活堆时，它和 `GOGC=100` 加同样的上限表现几乎一样，因为 goal 本来就是被上限卡住的。存活堆小一些时差别才出来：

`GOGC=off` 让堆一直涨到接近 230MiB 才回收，GC 次数少了六成，代价是常驻内存从 137MiB 涨到 225MiB。在内存配额按 limit 计费、而 CPU 紧张的场景，这笔交易是划算的；反过来就不划算。存活集 100MiB、都设 230MiB 上限时，`GOGC=100` 和 `GOGC=off` 的 goal 都是 212MiB，GC CPU 8.4% 和 8.7%，没有区别，因为两者算出的目标本来就差不多。

## 软上限：存活堆继续涨时，GC CPU 卡在 47% 然后被杀

`GOMEMLIMIT` 是软上限。文档写得很清楚：为了不让程序完全卡在 GC 上，运行时会把 GC 的 CPU 占用限制在大约 50%，超过之后宁可让内存越过上限。这意味着存活堆真的逼近上限时，它保不住进程。

我用 `GOMEMLIMIT=230MiB`、存活集 150MiB 起步、每秒再泄漏 1MiB 来模拟这个过程：

过程分三段：

存活堆越接近上限，goal 和 live 之间的空间越小，每分配一点就要触发一次 GC。从第 31 秒起，GC CPU 停在 47% 左右不再往上。我推测这是 CPU 限制器在起作用（文档说它把 GC 限制在约 50%）：GC 不能再快了，堆只能往上漫。不过这个 47% 含空闲标记时间，限制器是否按同一口径计算，我没有在文档里找到说明，所以这一条标为「推测」。第 37 秒最后一行日志之后，Pod 以 OOMKilled 137 结束（08:36:06 启动，08:36:43 结束）。

这次实验里垃圾产生速度是限速的 300MiB/s，CPU 上限 2 核还有余量，所以业务吞吐没有掉下来，表现为 GC CPU 一路上涨。如果不限速，同样的配置在第一次采样之前就被杀了。线上服务大多是后一种情况：请求不会因为 GC 忙就变少。

为了看清 GC 抢 CPU 对业务的影响，我另做了一组不限速的吞吐测试：存活集 120MiB，容器上限放宽到 1Gi，只改 `GOMEMLIMIT`：

两点值得注意。第一，上限从“不设”收到 230MiB，分配吞吐掉了 64%，而 GC CPU 只从 39% 升到 45%。这个指标已经包含辅助标记（mark assist）的时间，所以吞吐掉得比 GC CPU 涨得多的原因我没有拆开测，推测是 GC 周期变密后写屏障一直开着、分配更多走慢路径，这一条标为「推测」。第二，230MiB 及以下时 runtime 稳定在 255 至 275MiB，全都超过了设定值，软上限在这里看得很清楚。这组跑在 1Gi 的容器里，所以没有被杀；换成 256Mi 就是 OOMKilled。

## 堆外内存不在 GOMEMLIMIT 的账上

`GOMEMLIMIT` 只管 Go 运行时自己分配的内存。`runtime/debug.SetMemoryLimit` 的文档列出了不计入的部分：二进制文件本身的映射、其他语言（cgo）管理的内存、操作系统代程序持有的内存。我用 `syscall.Mmap` 申请 60MiB 并写满，模拟 cgo 库或 mmap 文件缓存：

Go 运行时认为自己只用了 197MiB，离 230MiB 还很远，所以不会加紧回收；cgroup 看到的是 255MiB。这时分配速度从 298MiB/s 掉到 9MiB/s，连采样本身也停了：1.03 秒那行之后的约 9 秒里程序一行都没打出来，所以 9MiB/s 是按被拉长的间隔算的。我推测进程被内核的直接回收拖住了，但没有采 `memory.stat` 或 PSI，这一条标为「推测」。大约 10 秒后 OOMKilled。

如果服务里有 cgo、大块 mmap 或者依赖库自带的内存池，`GOMEMLIMIT` 要从容器上限里先扣掉这部分，再留余量。

## 用 downward API 注入 GOMEMLIMIT，divisor 写错会让 GC 空转

把 `GOMEMLIMIT` 写死在镜像或 Deployment 里，改 limit 时容易忘记同步。常见做法是用 downward API 从容器自己的 `limits.memory` 读出来。这里有个容易踩的坑。

Downward API 那篇笔记提到过 `divisor` 的取整规则。对内存来说：

`divisor: 1Mi` 是最自然的写法，因为人习惯以 MiB 为单位。可 `GOMEMLIMIT` 接受的格式是“数字加可选单位后缀”，没有后缀就按字节解释，于是上限变成了 256 字节：

截图下半部分就是这个场景：`GOMEMLIMIT="256"`，`memlimit=0MiB`。程序启动 0.89 秒时已经做了 771 轮 GC，到 7.71 秒是 864 轮，平均每秒约 14 轮（另一次 1 秒采样的运行是每秒 16、17 轮），GC CPU 一直在 46% 左右。它并没有立刻崩，存活堆 167MiB 时 runtime 只有 182 至 197MiB，看起来比正常配置还省内存。但第 7.71 秒的最后一行里 runtime 突然到了 235MiB，同一行分配速度是 1099MiB/s，随后 Pod 被杀。

1099MiB/s 是我的限速器补偿造成的：GC 忙的时候分配被拖慢，限速器发现落后于 300MiB/s 的目标，就会连续补分配。我推测真实服务里请求积压后的突发也是类似效果，而 GC 已经满负荷，没有能力再收紧。这一点没有进一步验证，标为「推测」。

第三行同样是 256MiB，却在 19 秒左右被杀（Pod 级 `oom_kill 2`），而不写 divisor 的那次活过了 60 秒。两次的上限完全相同，`cg.peak` 都到过 249MiB 左右，一次被杀，一次没有。两次的差别我认为只是时机不同，但能确定的是 `GOMEMLIMIT` 设成和 limit 一样大没有余量。我推测把它推过线的是 Go 运行时之外的那点内存，比如二进制映射和内核代程序持有的内存，这一条没有单独测量。

我最后选的写法是先取 MiB，再乘一个比例。Kubernetes 的环境变量展开不支持算术，所以比例要么在启动脚本里算，要么在程序 `main` 开头用 `debug.SetMemoryLimit` 按 `memory.max` 设置。我这次没有测 `automemlimit` 之类的库。

## GOMAXPROCS：决定行为的是 go.mod 的 go 版本，不是工具链

Go 1.25 起，`GOMAXPROCS` 默认会参考 cgroup 的 CPU 上限，此前它只看主机的逻辑 CPU 数。这次我想确认的是：用新工具链编译老项目，会不会自动生效。

我构建了三种镜像，在 CPU limit 为 500m、1、1.5、2、4 核的 Pod 里各启动一次，只打印启动信息：

在 Docker 里用 `--cpus` 测了 1、1.5、2、4 核（没有测 0.5 核），结果一致。

原因在 GODEBUG 文档 里：新行为由 `containermaxprocs` 和 `updatemaxprocs` 两个 GODEBUG 开关控制，主模块 go.mod 的 `go` 行低于 1.25 时，它们的默认值是 0，也就是保持旧行为。所以只升级 CI 里的 Go 版本没有用，go.mod 的那一行才算数。

另外两个细节：

- 500m 得到的是 2 而不是 1。`runtime` 文档写明按 `ceil(quota/period)` 取整，且在 CPU 数不少于 2 时下限是 2。
- 1.5 核得到 2，向上取整。

GOMAXPROCS 也会影响内存。我在 CPU limit 2、内存 limit 1Gi 的 Pod 里跑不限速的负载（存活集 120MiB）：

GOMAXPROCS=26 的两组 GC CPU 只有 3.1% 左右（按 26 个 P 算），但存活堆在 3 秒内从 172MiB 跳到 346MiB 左右，堆目标随之翻倍，1Gi 都不够用。几组数字排除了两个直觉上的解释。一是 CPU 限流：Pod 级 `cpu.stat` 里 `nr_throttled 0`，`usage_usec` 约 4.27 秒，跑了约 4 秒，平均只用了 1 个核左右，2 核的配额没有用满。二是 GC 周期被拉长：26 个 P 时每秒 14、15 轮 GC，和 2 个 P 时差不多；GC 占用的绝对 CPU 也接近，3.1% × 26 和 40% 左右 × 2 都约是 0.8 个核。存活堆为什么在第 3 秒突然翻倍，我没有查清楚。能确定的是 `GODEBUG=containermaxprocs=1` 可以让 go.mod 还停在 1.24 的项目用上新行为，效果和升级 go.mod 一样。

这组实验每种配置只跑了一次，而且 GOMAXPROCS=2 的两次峰值也到了上限的 87% 至 95%，余量并不大。能说的是：在这组单次实验里，GOMAXPROCS 偏大的配置更早 OOM。go.mod 停在 1.24 的服务，即使 CPU limit 只有 2 核，运行时也会按 26 个 P 来安排 GC。

CPU 限流本身的现象在 探针与资源限制 里写过，Pod 的 QoS 等级对 OOM 时谁先被杀的影响见 QoS。

## 几个让我意外的地方

- 默认 GOGC 下真正决定峰值的是堆目标。存活 113MiB 时 Pod 峰值已是 230MiB，监控里只看 inuse 会严重低估。
- `GOMEMLIMIT` 设成和容器 limit 一样大，同样的值一次活过 60 秒，一次 19 秒被杀，没有稳定的结果。
- 在 `GOMEMLIMIT` 卡住的区间里，GC CPU 数字涨得不多（39% 到 45%），分配吞吐却掉了 64%，只看 GC CPU 指标会以为影响不大。
- downward API 加 `divisor: 1Mi` 的错误不会让程序立刻崩，反而让内存曲线看起来更低，只有 GC 次数（每秒 14 至 17 轮）和 CPU 能暴露它。
- 升级工具链不会自动启用容器感知的 GOMAXPROCS，要改 go.mod。

## 落地清单

根据这些数据，我现在给 Go 服务配内存时按这个顺序检查：

1. 先量存活堆，按 `存活堆 × (1 + GOGC/100)` 估算默认峰值。超过 limit 的 80% 左右就该设 `GOMEMLIMIT` 或者加 limit。80% 是经验值，这次没有逐档测；存活 113MiB 那次峰值到了 limit 的 90%，也活了下来。
2. `GOMEMLIMIT` 留出余量，比如 limit 的 90%。这次只测了两档：256Mi 下 230MiB（90%）可以长期运行，256MiB（100%）不稳定。
3. 有 cgo、mmap 这类 Go 堆之外的内存时，先从 limit 里扣掉，再算比例。
4. 用 downward API 注入时不要单独用 `divisor: 1Mi`。要么不写 divisor 拿字节数，要么拼上 `MiB` 后缀，要么在程序里读 `memory.max` 自己设置。
5. 设了 `GOMEMLIMIT` 后监控 `/gc/cycles/total:gc-cycles` 的增速和 GC CPU。GC 次数持续上涨、GC CPU 接近 50%，说明存活堆已经逼近上限，该扩容或查泄漏，不要指望它自己恢复。
6. 想少做 GC、内存又有富余时，可以试 `GOGC=off` 加 `GOMEMLIMIT`，但它只在存活堆远小于上限时才有区别。
7. 检查 go.mod 的 `go` 行。低于 1.25 时，要么升级它，要么加 `GODEBUG=containermaxprocs=1`，否则 GOMAXPROCS 还是主机核数。

- 语料和问题都是我一个人写的，中英文也是我自己对照着写的，难免带着我的措辞习惯。英文版不是专业译文。

- 嵌入是确定性计算，同一输入重复调用向量不变，所以每个组合我只跑了一次，没有重复取平均。

### 环境

Ollama 返回的向量已经做过 L2 归一化（`server/routes.go` 的 embed 处理里有 `normalize`），所以余弦相似度直接用点积算。

语料、问题和评测脚本放在 blog-go-example/local-embedding-chinese-retrieval，可以照着 README 复现。

## 中文比英文低一半

不加任何前缀时，四种组合的结果：

英文那一行几乎满分，40 条问题里 37 条第一名就对，前 5 名全部命中。说明问题和段落本身没有出错，同样的语义用英文表达，这个模型分得清。

中文这一行的 recall@5 是 0.8，看起来还能用，但 recall@1 只有 0.45。更说明问题的是最后两列：正确段落与问题的平均余弦是 0.700，而每条问题里「得分最高的错误段落」平均是 0.714。错误答案的分数平均比正确答案还高，排序几乎是在噪声里挑。英文这两个数是 0.715 和 0.609，中间有一段清楚的间隔。

## 词表里只有 244 个汉字

最先让我起疑的是两个相似度。我随手比了几对短语：

「存活探针失败」和「就绪探针失败」余弦 1.000，向量完全相同。「磁盘满了」和「天气很好」的相似度，比和「内存满了」还高。这不是语义理解弱能解释的，更像是这些字在模型眼里根本是同一个东西。

token 数也对得上这个猜测：「秋天」返回的 `prompt_eval_count` 是 4，「秋天的傍晚」是 7，正好是字数加 2（BERT 的开头和结尾标记），每个汉字一个 token。

于是我把语料和问题里出现过的 541 个不同汉字逐个送去嵌入，和一个生僻字「龘」的向量比较：

541 个汉字里有 470 个的向量和「龘」完全相同。按出现次数算，语料和问题里 78.8% 的汉字都变成了同一个 token。

为了确认这是词表本身的问题，而不是 Ollama 分词的实现问题，我用 `gguf` 这个 Python 包直接读了模型文件里的分词器元数据：

词表 30522 个 token，单个汉字只有 244 个。我的 541 个汉字里，71 个在词表中，正好就是上面那 71 个「能区分」的字，两种方法的结果完全吻合。「的」「一」「不」在词表里，「存」「活」「就」「绪」「容」「镜」都不在。30522 这个大小和 BERT 英文版词表一样，推测 nomic-embed-text 沿用了英文 BERT 的分词器，没有为中文扩充（我没有去核对它的训练代码，这一点是推测）。

这样再回头看中文 0.45 的 recall@1，就不奇怪它为什么不是 0 了：段落里的英文术语还在。我按问题里有没有英文字母把中文 → 中文的 40 条拆开：

纯中文问题第一名只对 27%。排名最差的几条全是纯中文：「怎么让服务崩溃后自动重启，又不会无限重启？」正确段落排到第 46 名（一共 48 段），第一名是启动探针那段；「改了配置，容器里的环境变量为什么还是旧的？」排第 35 名，第一名是多阶段构建。「怎」「么」「了」本身也是未知 token，推测模型实际上在用「不」「的」这类词表里有的常用字和标点去匹配。

## 前缀有一点用，但救不了中文

nomic-embed-text 的模型说明要求给查询加 `search_query: `、给文档加 `search_document: ` 前缀。我加上前缀重跑了一遍：

所有变化都在 1 到 2 条问题以内，有升有降，在这个样本量下分不出好坏。英文本来就接近满分，没有提升空间；中文的瓶颈在词表，前缀改变不了「存」和「就」是同一个 token 这件事。

前缀还有一个容易忽略的成本：它本身占 token。48 段中文文档的 `prompt_eval_count` 合计从 2448 变成 2640，多了 192 个，正好每段 4 个。对 2048 token 上限的模型来说不算多，但长文档切块时要算进去。

## 跨语言检索比中文对中文还差

如果中文问题去检索英文文档呢？思路是：既然英文这么好，能不能把知识库翻成英文，问题保持中文？

结果是 recall@1 0.350，比中文对中文的 0.450 还低。推测原因和上面一样：中文问题这一端已经变成了大量相同的未知 token，再好的英文文档也接不住。反过来英文问题查中文文档是 0.400，瓶颈换到了文档一端。

所以「文档翻成英文」只有在问题也翻成英文时才有意义，那时实际上就变成了英文对英文。

## 长文档在 2048 token 处被截掉

第二个担心是长文档。nomic-embed-text 的 Modelfile 里写着 `PARAMETER num_ctx 8192`，但模型元数据里的上下文长度是 2048。Ollama 嵌入时取两者较小的那个，源码在 `server/routes.go` 的 embed 处理函数里：

超出部分的处理和聊天接口不同。聊天接口截掉中间、保留结尾；嵌入接口是 `tokens[:ctxLen]`，保留开头、直接丢掉结尾。

我构造了一个测试：一句英文事实「The nightly backup job for the billing service runs at 03:17 and uploads its archives to the storage bucket named kestrel-archive.」，前面或后面拼上不同数量的填充句（用语料里其他英文段落循环拼接），问题是「When does the billing backup run, and which bucket does it upload to?」。

几个读数：

- 问题和事实句本身的余弦是 0.778，和 40 句纯填充文字是 0.523，这是两个参照点。
- 填充到 60 句以后，`prompt_eval_count` 停在 2048 不再增长。60、80、120、200 句的结果一字不差：事实在开头时余弦 0.640，在末尾时 0.528，后者和纯填充文字的 0.523 几乎一样，事实句已经被截掉了。
- 默认请求返回 200，没有任何提示。加 `"truncate": false` 后，同样的输入返回 400：`the input length exceeds the context length`。
- 同一时段的服务日志里没有 WARN。llama-server 每次请求都打一行 `stop processing: n_tokens = 2048, truncated = 0`，因为截断在 Ollama 这一层已经做完了，后端收到的输入本来就不超长。看到 `truncated = 0` 不能说明没被截。脚本按 truncat 或 WARN 统计到的 23 行，全是这种 slot release 行。

`prompt_eval_count` 能告诉你「到顶了」，但不会告诉你原文有多长。60 句的原文大约多长，我只能按 20 句 801 token、40 句 1564 token 的增量线性估，大约 2300 token 左右（估算，没有精确分词）。

还有一个比截断更早出现的效应。40 句填充时文档是 1564 token，没有被截断，但事实在末尾时余弦只有 0.544，在开头时是 0.635。我推测这和 nomic-bert 的平均池化有关：一句话的信息被 1500 多个 token 平均掉了，事实放在开头时略占优势的原因我没有深究。不管是哪种原因，在这组测试里，单个事实对整块向量的贡献很小，切块看起来比依赖长上下文更稳妥。

## 换成 bge-m3 之后

对照模型我选了 bge-m3，同样是 BERT 架构，但词表是为多语言训练的。同一套语料、同一批问题、同一个脚本，不加前缀：

中文对中文从 0.450 到 0.950，跨语言从 0.350 到 0.825。正确段落和最高错误段落之间重新出现了间隔（单语约 0.1，跨语言约 0.07），和 nomic-embed-text 在英文上的表现差不多。英文对英文 0.900 比 nomic 的 0.925 低一条问题，在这个样本量下算持平。

按问题里有没有英文字母拆开，bge-m3 的纯中文问题 recall@1 是 0.955（22 条），含英文字母的是 0.944（18 条），两类没有差别了。排名最差的一条是「排空节点时卡住不动，一直在等什么？」，正确段落（PodDisruptionBudget）排第 12，第一名是数据库连接池那段，两段都在讲「等待」。这种错误至少是语义上能理解的。

之前那几对短语也换 bge-m3 算了一遍：

「磁盘满了」终于离「内存满了」比离「天气很好」更近。分词也不再是逐字：「秋天的傍晚」是 6 个 token（含首尾标记），比 nomic 少 1 个；48 段中文文档的 token 合计 2048，比 nomic 的 2448 少 16%。

代价在体积上。`ollama list` 里 bge-m3 是 1.2 GB（567M 参数，F16，1024 维），nomic-embed-text 是 274 MB。按默认参数加载后，`ollama ps` 显示 bge-m3 占 664 MB（CONTEXT 4096），nomic 占 323 MB（CONTEXT 2048），都在 GPU 上；后面把 bge-m3 的 num_ctx 提到 8192 时变成 940 MB。速度反而没拉开：48 段中文一次批量嵌入，nomic 三次分别是 366、238、193 ms，bge-m3 是 337、334、334 ms。每种各 3 次计时，GPU 上的批量很小，换成 CPU 或大批量结论可能不同。

## 这次的局限

- 语料只有 48 段、40 条问题，全部出自我一人之手；领域集中在运维和后端开发。换成长篇、口语化或者专业领域的中文，数字会不一样。
- 只比较了 nomic-embed-text 和 bge-m3 两个模型，没有测其他中文嵌入模型。
- 长文档实验只用了英文填充文字和一个事实句，每个长度一次；速度只计了三次，都是单次运行的读数。
- 「词表里只有 244 个汉字」是 Ollama 发布的这个 GGUF 文件的情况，我没有核对其他来源或其他格式的 nomic-embed-text 权重。

## 中文知识库选嵌入模型前的三个小测试

下面几个小测试一分钟就能跑完，换任何嵌入模型都可以先过一遍。

第一个是「生僻字测试」。拿语料里出现过的汉字逐个嵌入，和一个肯定不在词表里的字（我用的是「龘」）比较，向量完全相同的比例就是落进未知 token 的比例。nomic-embed-text 是 470/541。再加两三对「意思不同但字数相同」的短语，余弦接近 1 就该警惕。

第二个是看 `prompt_eval_count`。它比字数更直接地告诉你模型怎么切中文：每个汉字一个 token 说明词表没有中文词，同时它也是判断截断的唯一读数，等于 2048 这种整数时，多半是被截了。

第三个是在入库脚本里固定写 `"truncate": false`。默认的静默截断对检索的伤害是看不见的，宁可让超长的块报 400，再回去改切块大小；真的需要长上下文，就同时设 `num_ctx` 和 `num_batch`，并在日志里确认没有 `too large to process`。

至于 nomic-embed-text，它在英文上的成绩我没有任何意见，40 条问题 37 条第一名命中。只是在一个以中文为主的知识库里，它的大部分汉字是同一个 token，用上面的词表检查就能提前发现。

给一个 Go 服务加副本，监控上新 Pod 的 QPS 却一直贴着 0，这是 HTTP 长连接遇上 Kubernetes Service 的老问题。kube-proxy 只在建立连接时挑后端，连接一旦建好，后面的请求都跟着它走。

我在本机用 kind 起了一个一次性集群，写了一个按秒统计"每个 Pod 回了多少请求"的 Go 客户端，在运行中途把 Deployment 从 2 扩到 4，然后逐个测常见的几种修法。默认配置下，扩容后 35 秒里新 Pod 的请求占比是 0%。效果最稳的是服务端每处理 100 个请求就回一次 `Connection: close`，新 Pod 占比到了 49.6%（理想值 50%）。客户端定时 `CloseIdleConnections` 只到 20%，调小 `IdleConnTimeout` 毫无作用，h2c 把所有请求塞进一条连接，800 rps 也只落在 1 个 Pod 上。

## 实验环境与测试程序

集群只为这次实验创建，kubeconfig 单独写在实验目录，所有 `kubectl` 都显式带 `--kubeconfig`，做完后集群和镜像都删掉了。

服务端、客户端、Dockerfile 和跑实验的 kind 脚本放在 blog-go-example/keepalive，可以照着 README 复现。

服务端 `echo` 每个请求先睡 10ms 模拟业务处理，再把自己的 Pod 名写进响应头 `X-Pod`。它支持几个开关：`MAX_REQS_PER_CONN` 控制一条连接上处理多少个请求后回 `Connection: close`，`H2C` 打开明文 HTTP/2，`SHUTDOWN_DELAY` 控制收到 SIGTERM 后先让 `/ready` 返回 503、等多久再调用 `Server.Shutdown`。

客户端用 8 个 goroutine 合计每秒发 200 个 GET，跑 60 秒，每秒打印一行：

`dials` 是这一秒里新建的连接数，用 `httptrace` 的 `GotConn` 回调统计 `Reused=false` 的次数；后面是这一秒每个 Pod 回了多少个 200。每次实验的流程是同一个脚本：部署 2 副本，等就绪，启动客户端 Pod，第 20 秒执行 `kubectl scale --replicas=4`，等客户端跑完收日志。

后文用到的两个指标：

- **新 Pod 占比**：第 26～60 秒这 35 秒里，扩容新建的 2 个 Pod 回复的请求数除以全部成功请求数。4 个 Pod 平分时是 50%。前 5 秒留给新 Pod 启动和就绪。有记录的几次里，新 Pod 从创建到 Ready 用了 2～7 秒；早期几次没记 Ready 时间，从服务端日志看，有两次新 Pod 在扩容后约 20 秒才开始监听，这两次会在后文单独说明。
- **新建连接/秒**：同一窗口里 `dials` 的平均值，用来看一个方案要付出多少次重新建连。

除非特别注明，每个配置只跑了一次。

## 默认配置：扩容后新 Pod 一个请求都没有

第一次跑默认配置（`http.Transport` 全用默认值），整整 60 秒只有开头建了 2 条连接，而且这 2 条恰好都落在同一个 Pod 上。扩容之前，另一个旧 Pod 也一个请求都没收到：

服务端日志显示，两个新 Pod 在扩容后 8～9 秒（客户端第 28 秒左右）就开始监听了，客户端跑完时 4 个 Pod 都在。第二次跑同样的配置，开头建了 4 条连接，两个旧 Pod 分到 49% 和 50%，新 Pod 依然是 0%。两次的差别只在于开头那几条连接被随机分到了哪里。

原因写在 Kubernetes 文档的 Virtual IPs and Service Proxies 里：iptables 模式下，kube-proxy 为每个端点装的规则"by default, select a backend Pod at random"，而这个选择发生在"When a client connects to the Service's virtual IP address"。选中之后，这条 TCP 连接上的所有数据包都去同一个 Pod。Go 的 `http.Transport` 默认会复用连接，`DefaultTransport` 的 `IdleConnTimeout` 是 90 秒，每个 host 最多保留 2 条空闲连接（`DefaultMaxIdleConnsPerHost = 2`）。只要请求不断，连接就不会空闲，也就永远不会重新经过 iptables 的那次随机选择。Service 本身的工作方式可以参考 Service 笔记。

这个客户端并发不高：10ms 的处理时间、每秒 200 个请求，同时在途的请求平均只有 2 个左右，所以 2～4 条连接就够用。真实环境里调用方往往是很多个 Pod，每个都带着自己的几条连接，整体看会比这里均匀一些，但"扩容后只有新建的连接才会去新 Pod"这一点不变。

## 七种修法放在同一个负载下比较

下面每一行都是同一个负载（8 个 worker、200 rps、10ms 处理时间、第 20 秒扩到 4 个副本）下单独跑一次的结果：

### 服务端限制每条连接的请求数，效果最直接

服务端的改动只有几行。用 `ConnContext` 给每条连接挂一个计数器，处理到第 N 个请求时在响应头里加 `Connection: close`：

Go 的 HTTP/1.1 服务端看到处理器设置了 `Connection: close`，写完这个响应就关掉连接；客户端下一次请求只能重新拨号，重新经过一次 iptables 的随机选择。N=100 时，扩容后第 4 秒新 Pod 就开始出现在日志里：

N 越小，收敛越快，代价是建连越频繁。N=1000 那次，两个新 Pod 分别在扩容后第 9 秒和第 13 秒才拿到第一个请求，35 秒窗口里的占比也到了 46.4%，但 4 个 Pod 之间并不均匀（17% 到 34%）。因为连接只有三四条，每次重连落在哪个 Pod 都是一次随机抽签，抽签次数少，分布就不稳。

按 200 rps、每连接 100 个请求算，应该每秒重连 2 次，实测平均只有 1.1 次。我没有查清差在哪里，推测和 Go 客户端的拨号方式有关：一个请求在等新连接时如果先等到了别的空闲连接，新拨好的那条会进空闲池，之后被取出时 `GotConn` 报告为复用，没被计入 `dials`。所以这一列更适合横向比较，不宜当成精确的建连次数。

### 客户端侧的三个参数，只有一个勉强有用

`IdleConnTimeout=5s` 完全没效果，结果和默认配置一样。这个超时只对空闲连接计时，而每秒 200 个请求下连接从来没有空闲过 5 秒。

`MaxConnsPerHost=1` 更糟。它限制的是到同一个 host 的连接总数，结果所有请求排队挤在一条连接上：每个请求要 10ms，一条 HTTP/1.1 连接一秒最多 100 个，日志里每秒稳定在 97、98 个，35 秒只完成了 3410 个，比目标少了一半多，而且这条连接上的流量全在 1 个 Pod 上。

每 5 秒调一次 `tr.CloseIdleConnections()` 拿到了 20%。它的文档写得很清楚："It does not interrupt any connections currently in use"。在持续负载下，调用那一刻碰巧空闲的连接才会被关掉，日志里每 5 秒恰好出现 1 次新建连接，扩容后 35 秒一共只有 7 次重新抽签的机会，结果只有 1 个新 Pod 分到过流量，另一个一直是 0。

### 客户端并发上去以后，默认配置反而"自己均衡"了

把客户端改成 32 个 worker、800 rps，同样默认配置，跑了两次，新 Pod 占比分别是 23.2% 和 50.6%，新建连接每秒 23.1 次和 19.5 次。连接一直在被关掉又新建。

原因是 `MaxIdleConnsPerHost` 的默认值 2。并发请求多于 2 个时，请求结束后归还连接，空闲池已经有 2 条了，多出来的就直接关闭；下一个请求来时池子不够，又得新拨。这种"抖动"让连接不断重新抽签，看上去把流量分到了新 Pod，代价是每秒二十多次 TCP 建连。

把 `MaxIdleConnsPerHost` 设成 32 再跑一次，新建连接立刻降到 0，新 Pod 占比也掉到 5.1%：两个新 Pod 里一个拿到 5%，另一个是 0。很多文章建议把 `MaxIdleConnsPerHost` 调大以减少建连开销，这个建议本身没错，但调大以后，原来靠抖动掩盖的不均衡就会显露出来。

两次结果差一倍，不能当成随机波动。从服务端日志看，第一次运行的两个新 Pod 在扩容后约 21 秒才开始监听，到第 44 秒才收到第一个请求（第二次是第 25 秒），窗口里只剩十几秒能接流量，所以 23.2% 偏低。新 Pod 为什么启动慢没有查到。

## Headless Service 加客户端轮询：比较均匀，但要等 DNS

Headless Service（`clusterIP: None`）不经过 kube-proxy，DNS 直接返回所有就绪 Pod 的 IP。客户端每 5 秒解析一次，然后按 IP 轮询：

Go 的连接池按 host:port 区分，所以每个 Pod IP 有各自的连接，轮询到哪个 IP 就用哪个 IP 的连接，分布可以做到很均匀。第二次运行我让它跑 90 秒，并在解析结果变化时打印一行：

一旦拿到 4 个 IP，每个 Pod 每秒 49～51 个请求，是所有方案里最均匀的，而且不需要任何重连。问题在于等待：两个新 Pod 在客户端第 23、24 秒就 Ready 了，DNS 到第 35 秒之后才返回它们。kind 的 CoreDNS 配置里有 `cache 30`，客户端第 0 秒的那次查询被缓存了 30 秒，这和 35 秒才看到新 IP 吻合，但我没有单独验证，算推测。按 26～90 秒算，这次的新 Pod 占比是 42.3%。

第一次 headless 运行只跑了 60 秒，扩容后整整 40 秒都只解析到 2 个 IP，新 Pod 占比 0%。那次客户端还没加打印解析结果的代码。服务端日志显示那次新 Pod 扩容后约 19 秒才开始监听，加上 30 秒的 DNS 缓存，60 秒内看不到新 IP 并不意外，但这同样是推测。

这个方案还有两个代价：客户端要自己处理 DNS 刷新和 Pod 下线（IP 消失后要停止使用并关掉对应连接，我的测试程序没做这部分）；另外它绕开了 Service 的 ClusterIP，sessionAffinity 之类的 Service 配置也就不再生效。几种 Service 类型的区别可以看 Service 类型笔记。

## h2c 只用一条连接，问题最严重

换成明文 HTTP/2（Go 1.24 起可以用 `http.Protocols` 的 `SetUnencryptedHTTP2` 在服务端和客户端同时打开），客户端对同一个 host 只建 1 条连接，所有请求在这条连接上多路复用：

8 worker 和 32 worker 两次运行都是这样：60 秒里只建 1 条连接，扩容前另一个旧 Pod 也是 0，扩容后新 Pod 还是 0。HTTP/1.1 下高并发至少还会多开几条连接、偶尔抖动一下，HTTP/2 连这点随机性都没有了。gRPC 默认也跑在 HTTP/2 上，推测会有同样的问题，这次没有测 gRPC。

服务端每 100 个请求回 `Connection: close` 对 h2c 同样有效，新 Pod 占比 45.0%，新建连接正好每秒 2.0 次。HTTP/2 协议里不允许 `Connection` 这个头，Go 服务端看到处理器设置它时会改为结束这条连接，具体是不是通过 GOAWAY 实现的我没有抓包确认，只看到了每秒 2 次的重连。

## 滚动更新：错误很少，但更新完可能只剩一个 Pod 在干活

最后看 `kubectl rollout restart` 时客户端能看到什么。2 个副本，第 20 秒触发滚动更新，每种配置跑一次：

错误数是"失败请求数 / 总请求数"。所有错误都是 `connection refused`，原始日志见本节后面那张截图的下半部分。

错误这么少，是因为 Go 客户端会自动重试。`net/http` 文档写的是：只有在连接"has already been used successfully"、且请求是幂等的（GET、HEAD 等）时才会在网络错误后重试。旧 Pod 关闭时，复用中的连接被关掉，客户端在新连接上重发 GET，调用方看不到错误。剩下的 `connection refused` 出在新拨的连接上，新连接不满足重试条件。有两次错误和旧 Pod 被删除发生在同一秒，我推测是 Pod 已经停止监听，iptables 规则还没删掉这个端点；但我没有记录端点变化，无探针的运行里也可能是新 Pod 还没监听就已经算 Ready（有一次错误比新 Pod 开始监听只早 1 秒）。换成 POST 这类非幂等请求，复用连接上的失败也不会被重试，错误应该会更多，这一点我没测，是推测。

8 worker 下错误只有 0 或 1 次，每种配置跑一次，看不出只加 readinessProbe 有没有用；有说服力的只有 32 worker 下 13 次对 0 次，而那一档没测只加 readinessProbe 的情况。按 Kubernetes 的终止流程，Pod 被删除时，从 Endpoints 里摘除和向容器发 SIGTERM 是同时开始的，服务端收到 SIGTERM 立刻 `Shutdown`，不再接受新连接，而 kube-proxy 可能还没更新规则。`preStop` 里先 sleep 5 秒，或者应用收到 SIGTERM 后先把 `/ready` 置为失败、继续服务 5 秒再关，都给了规则更新的时间，两种做法在这几次运行里都是 0 错误。v1.31 的集群里可以直接用 `lifecycle.preStop.sleep`，测试镜像是 `FROM scratch`，里面没有 `sleep` 命令，这个字段正好省事。优雅终止的完整流程可以看 优雅终止笔记。

更值得注意的是最后一列。滚动更新逐个替换 Pod，旧 Pod 关闭时客户端要重连。我推测重连那一刻经常只有第一个新 Pod 已经 Ready，连接于是全落在它身上，这次没有记录每个时刻的端点列表来证实。4 次 8 worker 的运行里，有 2 次更新结束后 200 rps 全在一个新 Pod 上，另一个新 Pod 一直是 0：

也就是说，长连接的不均衡不只在扩容时出现，每次发版都可能重新制造一次。Deployment 的滚动参数（maxSurge、maxUnavailable）决定了替换的节奏，见 Deployment 笔记。

## 几个让我意外的地方

- 扩容前就不均衡。默认配置第一次运行时，2 个旧 Pod 里有 1 个从头到尾没收到请求。连接少的客户端，副本数多少都一样。
- 默认 `MaxIdleConnsPerHost=2` 在高并发下造成的连接抖动，碰巧起到了均衡作用。这一次把它调大到 32 后，新 Pod 只拿到 5.1%。
- 调 `IdleConnTimeout` 是最常见的建议之一，在持续有流量的服务上完全无效。
- `MaxConnsPerHost` 限的是连接总数，不是单条连接的寿命，在每个请求 10ms 的负载下，设成 1 让吞吐只剩一半。

## 新 Pod 分不到流量时，先看连接数

从这些数据看，判断和处理的顺序可以是这样：

1. 先确认是不是长连接造成的：看调用方到这个 Service 一共有多少条连接、新连接的建立速率。连接少、几乎不新建，就是这次复现的情况。
2. 能改服务端就在服务端限制每条连接的请求数（或连接存活时间）。这次 N=100 在 4 秒内就让新 Pod 拿到流量，每秒只多 1～2 次建连；N 取多大取决于调用方的请求速率，我只测了 100 和 1000 两档。
3. 只能改客户端时，`CloseIdleConnections` 定时调用有一点作用（这次 20%），`IdleConnTimeout` 和 `MaxConnsPerHost` 不要指望。
4. HTTP/2、gRPC 这类单连接多路复用的协议，服务端限制连接寿命几乎是必需的，否则扩容和发版后都可能只有一个 Pod 在干活。
5. 需要真正均匀、又能接受在客户端维护 Pod 列表时，用 Headless Service 加客户端负载均衡，同时要考虑 DNS 缓存带来的十几秒延迟和 Pod 下线的处理。
6. 发版时加 `preStop` 等待或在应用里延迟关闭，减少 `connection refused`（这次 32 worker 下从 13 次降到 0）；发版后再看一眼各 Pod 的流量分布。

## 测试环境和测法

系统提示词是一份程序生成的"值班手册"：80 条格式相同、内容随机的处置规则，qwen2.5-coder 分词后 6269 个 token，llama3.1 是 6733 个。用户问题固定为一句话。每次请求 `temperature: 0`、`seed: 1`、`num_predict: 24`，只生成 24 个 token，让时间主要花在提示词上；多轮和工具循环两组为 60。

客户端用 Python 直接发流式请求，记录四个数：

- `prompt_eval_count` 和 `prompt_eval_cached_count`：提示词总 token 数和其中命中缓存的数量。
- `prompt_eval_duration`：提示词处理耗时。
- `load_duration`：加载模型的耗时。
- 首字延迟（TTFT）：从发出请求到收到第一段正文的时间，在客户端测量。

除特别说明，每种情况连续跑 5 次（个别 6～7 次），下文给中位数，括号里是范围。测试期间这台机器的 CPU 上还跑着另一个实验，负载在 12～15 左右，GPU 上没有别的推理任务，每批测试前用 `nvidia-smi` 确认过。提示词处理本身在 GPU 上，受影响应该不大，但首字延迟里的几毫秒抖动不必当真。

测试脚本放在 blog-go-example/ollama-prefix-cache，可以照着 README 复现。

先说一个读数上的坑：`prompt_eval_count` 不能用来判断有没有命中缓存。命中时它照样报 6269，因为 Ollama 把缓存命中数和实际计算数加在一起返回（v0.35.0 的 `llm/llama_server.go` 里 `promptEvalCount()` 返回 `CacheN + PromptN`）。要看的是 0.35.0 响应里多出来的 `prompt_eval_cached_count`，或者 `prompt_eval_duration`。`/v1` 接口对应的是 `usage.prompt_tokens_details.cached_tokens`。

## 缓存命中和没命中差多少

命中时最多是 6268，比总数少 1：最后一个 token 总要重新算一次，才能拿到生成第一个字所需的输出。缓存为空时，提示词处理按每秒约 2130 个 token 算，6269 个就是 2.9 秒。模型文件已经在系统页缓存里，加载只要 1.8 秒；第一次从磁盘读时要久得多，后面会说到。

在一个槽位内，规则只有一条：llama-server 拿新请求的 token 序列和缓存里的序列从头比较，取最长公共前缀，前缀以内直接复用，从第一个不同的 token 起全部重算。所以要问的不是"改了什么"，而是"第一处改动离开头有多远"。

## 时间戳放在哪：开头 3.1 秒，结尾 69ms

很多程序会往系统提示词里塞当前时间、请求编号或用户名，好让模型"知道现在几点"。我在每次请求里生成一个精确到微秒的时间和一个随机请求号，分别放在三个位置：

放在开头时只能命中 3～24 个 token，也就是模板开头的标记，加上时间字符串里相邻两次请求恰好相同的那一小段。剩下 6000 多个 token 每次都要重算，首字延迟是完全命中时的 80 多倍。放到结尾或用户消息里，变化的只有最后几十个 token，比完全命中多 30ms 左右。

llama3.1:8b 上结果一样：开头 3547ms（3543～3558），结尾 45ms（44～53），用户消息里 44ms（43～55）。

时间戳只是最常见的一种。凡是每次请求都会变的东西，比如会话 ID、用户名、"今天是星期几"、随机挑选的示例，只要写在系统提示词前面，效果都一样。

## 工具定义：顺序变了要重算近 800 个 token，llama3.1 每轮都要

给请求加上 8 个工具定义后，提示词变成 7084 个 token。每次请求把工具列表随机打乱一下：

工具这一组我只看提示词处理时间，不看首字延迟：模型返回的是工具调用，正文要等调用解析完才有，首字延迟测出来没有意义。

qwen2.5-coder 的模板把工具定义放在系统提示词后面，所以前面 6277 个 token 还能复用，只重算工具那 800 来个 token。按 Python dict 遍历顺序、或者按插件注册顺序拼工具列表的程序，顺序通常是稳定的；从集合里取、或者按"相关度"动态挑选工具的程序就不一定了。

真正的坑在 llama3.1:8b 的模板里。`ollama show llama3.1:8b --template` 能看到，它不把工具放进系统提示词，而是放在**最后一条用户消息**里（模板里的 `{{- if and $.Tools $last }}`）。多轮对话时，上一轮的用户消息不再是"最后一条"，工具定义就从那里消失，挪到新的用户消息后面。结果是工具定义永远在提示词末尾，永远进不了缓存。

我用同一组工具跑了一个 5 轮的工具调用循环（用户提问、模型调用工具、程序回填一条工具结果、模型回答）：

llama3.1 每轮都要重算 840 多个 token，提示词处理比 qwen 多约 470ms；工具结果回填后的那次请求，工具定义不渲染，只要 62～65ms。qwen2.5-coder:7b 这组需要说明一下：它把工具调用当成正文 JSON 输出，Ollama 没解析成 `tool_calls`（上一篇遇到过同样的情况），所以循环里没有工具结果这一步，只是普通的多轮追加。但 qwen 的模板里工具在系统提示词后面，位置不随轮次变化，这一点和有没有解析出工具调用无关。

## 多轮对话：追加没问题，从头裁历史就有代价

多轮对话最自然的写法是每轮把新的用户消息和模型回答追加到消息列表末尾，前面的内容不变，缓存一直有效：

每轮没命中的 34～36 个 token 就是新的用户问题。模型上一轮生成的回答，下一轮作为 assistant 消息重新分词后，和缓存里的 token 对得上，这一点在 qwen2.5-coder 上是成立的。

滑动窗口是为了控制上下文长度：消息超过 5 条以后，每轮从最前面丢掉旧的。丢的位置紧跟在系统提示词后面，于是缓存只能命中系统提示词那 6239 个 token，整段保留下来的历史每轮都要重算。我这组的回答只有 60 个 token，历史很短，代价是每轮多 85ms 左右；历史越长，这个数越大。按 2130 token/s 粗算，保留 4000 token 的历史，每轮要多花近 2 秒（推测，没有实测这个长度）。

想要控制长度又不想每轮都失效，可以攒到一定长度再一次性裁掉一大段，让缓存在两次裁剪之间保持有效。这是从机制推出来的做法，我没有单独测。

## 改采样参数没事，改 num_ctx 等于重新加载

温度、top_p 这类采样参数只影响生成阶段，缓存照常命中。`num_ctx` 不同就是另一回事：Ollama 的调度器发现运行参数变了，会把模型卸载再按新参数加载一遍，缓存跟着进程一起没了。v0.35.0 的 `server/sched.go` 里 `needsReload` 比较的是 `api.Runner` 这组参数，包括 `num_ctx`、`num_batch`、`num_gpu`、`main_gpu`、`use_mmap`、`num_thread`，任何一个和已加载的模型不同都会触发重载。

一个应用里不同功能用不同的 `num_ctx`（比如聊天用 8192，总结长文用 32768）时，两类请求交替到来，每次切换都要付 5 秒多。

## /v1 和原生接口混用：上下文对不上就每次重载

`/v1/chat/completions` 不认 `num_ctx`（上一篇测过，`options` 整个被丢掉），总是用服务的默认上下文，这台机器上是 4096。所以这组换成一份 2780 token 的短提示词：

上下文一致时，两个接口渲染出来的提示词完全相同，互相命中对方留下的缓存。原生接口带了 `num_ctx: 8192` 后，每次从 `/v1` 切回原生都要按 8192 重载，从原生切到 `/v1` 又要按 4096 重载。原生侧测到每次加载约 2.4 秒，`/v1` 侧首字延迟 3.7～4.2 秒，量级相同。同一个服务里一部分代码用 OpenAI SDK、一部分直接调原生接口，就会碰到这个情况。解决办法是把上下文长度定在一处：用 `OLLAMA_CONTEXT_LENGTH` 或 Modelfile 的 `PARAMETER num_ctx`，两边都不在请求里传（这个做法我没有实测）。

`/api/generate`（`system` + `prompt`）和 `/api/chat` 也能互相命中，5 组交替请求里每次都命中 6268 个 token。

## 别的模型、keep_alive 和多份提示词

**加载另一个模型。** 中间穿插一次 qwen2.5-coder:0.5b 的请求，两个模型能同时放进显存，7b 的缓存不受影响，下一次请求照样 16ms。换成 llama3.1:8b 就放不下了，Ollama 把 7b 卸掉，切回来时要重新加载再重算：后 4 次加载 2.4 秒（2.38～2.68），提示词处理 2.9 秒，首字延迟 5.4 秒。这组的第一次加载花了 129 秒，模型放在机械硬盘上，我推测是模型文件当时不在页缓存里。

**keep_alive 过期。** 请求里设 `keep_alive: "5s"`，等 8 秒后再发，模型已经被卸载，5 次都要从头来过，首字延迟 4.7 秒（4.5～4.8）。服务默认的 5 分钟在交互场景下一般够用；如果是间隔几分钟才来一次的定时任务，第一次请求总要付加载加重算的钱。

**两三份提示词轮流用。** 这是唯一让我意外的结果。`OLLAMA_NUM_PARALLEL=1` 时 llama-server 只有一个槽位，我以为两份不同的系统提示词交替使用会互相挤掉缓存。实测并没有：P1、P2 交替 6 轮，三份 P1、P2、P3 轮流 5 轮，除了每份提示词第一次出现那一次，其余全部命中，`prompt_eval_duration` 都在 16～19ms。

但首字延迟是 210ms 左右，不是 37ms：

服务端日志说明了原因。llama.cpp 的服务端有一个放在**内存**里的提示词缓存（PR #16391）：切换提示词时，先把当前槽位的 KV 状态整份存进内存，这次是 344 MiB；再从已存的几份里找公共前缀最长的那份，拷回显存。这一存一取花了 135～229ms，中位数约 170ms，而且不算在 `prompt_eval_duration` 里，只有在客户端测首字延迟才看得到。

这个缓存默认上限 8192 MiB（llama.cpp b11081 的 `common/common.h` 里 `cache_ram_mib = 8192`），Ollama 0.35.0 启动 llama-server 时没有改这个参数。按日志里 `149764 est` 的估算，这样大小的提示词能存二十多份，超出后从最旧的开始丢，这个上限我没有测到。这块内存占的是系统内存，不是显存；内存紧张的机器上要算进去。

排查时先看 `prompt_eval_cached_count` 和 `prompt_eval_count` 的比例，接近 1 就是命中；再看 `load_duration`，超过几十毫秒说明模型被重新加载了。两项都正常、首字延迟却明显偏高时，去 `journalctl -u ollama` 里搜 `prompt cache update took`，看是不是在内存缓存里换来换去。

## 这次没测的

- `OLLAMA_NUM_PARALLEL` 大于 1 时，多个槽位各有自己的缓存，请求被分到哪个槽位会影响命中率。
- 开启 Flash Attention 或量化 KV 缓存（`OLLAMA_KV_CACHE_TYPE`）后，重算速度和内存缓存每份的大小都会变。
- 提示词只测了 2780 和 6000～8000 token 两档；更长的提示词，重算和内存缓存存取的绝对耗时都会更大。
- 每种情况只在一个下午里连续跑了 5 次左右，不同硬件上的绝对数字会不一样，但在 llama-server 默认配置下，"第一个不同的 token 之后全部重算"这条规则不变。
